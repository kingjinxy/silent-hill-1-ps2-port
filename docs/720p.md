# 720p and widescreen: feasibility (2026-10-19)

Findings on high-definition output and widescreen for the PS2 port's GS renderer (src/port/ps2/gpu_gs.c). Not implemented yet. The GS has 4 MB of local memory, and everything below is budgeted against that.

## Current renderer, for reference

- **PS1 VRAM:** a 1 MB 16-bit image (1024x512) lives in GS memory. The game draws into it, and 4/8-bit texture pages and CLUTs are read back from it into a GS-side cache.
- **Shadow buffer:** the Debug Options "Resolution" (x1/x2) and "Color Depth" (16/32-bit) settings draw the frame-buffer area (VRAM x 0-319, y 0-511) into a separate shadow buffer. Tiles drawn there are scaled down into VRAM only when something reads them.

| Mode | Shadow buffer | Texture page cache |
|---|---|---|
| 1x 16-bit | none | 37 slots of 64 KB |
| 1x 32-bit | 640 KB | 37 |
| 2x 16-bit | 1.25 MB | 27 |
| 2x 32-bit | 2.5 MB | 7 |

With 7 slots (2x 32-bit), the Kaufmann cutscene (Demo 4) re-read 9-14 texture pages from VRAM every frame in PCSX2. So a busy scene needs more than 7 pages, and readbacks are the most expensive operation on hardware.

## Why the game is 224 / 448 lines

- Silent Hill sets the heights itself: `FRAMEBUFFER_HEIGHT_PROGRESSIVE 224` and `FRAMEBUFFER_HEIGHT_INTERLACED` (448) in include/game.h.
- NTSC has 240 lines per field, but many PS1 games draw 224. The outer lines are lost to TV overscan anyway, and it saves VRAM and fill time. The PS1 centres the 224 lines with black borders, and the port does the same.
- 240/480 lines would be a game change, not a renderer setting: the clip areas, buffers, camera view and 2D layout would all have to cover more lines.

## 720p

**Picture size**
- 320x224 at 3x is 960x672. That fits a 1280x720 frame with black side bars, so 4:3 is kept.
- The scale doesn't have to be an integer: GS vertex coordinates are 12.4 fixed point. About 2.8x horizontally and 3x vertically gives the correct aspect (about 896x672).
- The 640x448 menus scale 1.5x to the same size.
- One fixed 720p output would also end the TV re-syncs on video mode changes.

**Fill rate:** 9x the 1x pixel count is still a small fraction of the GS's capacity.

**GS memory**

| | 720p, VRAM kept on the GS | 720p, VRAM moved to EE RAM |
|---|---|---|
| PS1 VRAM copy | 1 MB | none |
| Screen buffers (only the two display buffers, 960x672x2 each) | 2.5 MB | 2.5 MB |
| CLUT cache | 64 KB | 64 KB |
| Texture page cache | about 7 slots (thrashes) | about 23 slots (like today's 2x 16-bit) |

**Conclusion:** 720p fits only if the PS1 VRAM image leaves GS memory, and if the shadow buffers cover only the two display buffers instead of the whole 320x512 area. 32-bit colour at 720p isn't possible: two 960x672 32-bit buffers alone need 5 MB.

### Texture streaming (the key piece)

- **EE-side VRAM:** keep the PS1 VRAM image in EE RAM (1 MB; about 3 MB is free).
- **Uploads instead of readbacks:** feed the GS texture page and CLUT caches by upload from that image. An upload is a fast one-way DMA; a readback stalls the GS, the DMA and the EE. This should also speed up today's 1x/2x modes, since readbacks drop to zero.
- **Why the GS copy isn't needed** (from the screen-read inventory, Running Walkthrough.md):
  - The game never draws into texture pages.
  - Its only screen reads are the motion-blur effects, served from the screen buffers, and the lens-flare occlusion test, a small readback of the screen buffer.
- **Other VRAM operations move to the EE copy:** LoadImage, fills and VRAM-to-VRAM copies outside the screen buffers.

### Suggested order (each step testable on its own)

1. **Texture streaming:** move VRAM to EE RAM and feed the texture/CLUT caches by upload. Measure misses and upload time per frame in PCSX2 and on the console.
2. **Display-buffer shadows:** shadow only the two display buffers, at any (non-integer) scale, not the whole 320x512 area.
3. **Drop the GS VRAM copy:** lay GS memory out for 720p.
4. **720p output:** gsKit's 720p mode with side bars; menus and movies scaled into the same buffers.

**Unknowns:** the texture working set of busy scenes, and the upload speed on hardware. Step 1 measures both.

## Widescreen

### A true 1280-wide framebuffer doesn't fit

- A 1280x720 16-bit buffer is 1.8 MB. The game draws into one buffer while the other is shown, so it needs two: 3.7 MB of the 4 MB.
- Even with VRAM in EE RAM, that leaves about 0.3 MB for textures (about 4 cache slots), far below the measured working set.

### Anamorphic widescreen, as PS2 games did it

- The buffer keeps its width. The game draws a 16:9 view squeezed horizontally into it, and the TV (in 16:9 mode) stretches it back. This costs no extra GS memory and works with 1x, 2x and 32-bit.
- For 720p, a 640x720 buffer doubled horizontally by the display hardware (MAGH) would be 0.9 MB per buffer instead of 1.8 MB.
- To check on hardware: which framebuffer widths and MAGH values the GS accepts in 720p and 480p.

### Work in the game (source available)

1. **Projection:** narrow the 3D projection horizontally by 3/4 (the GTE screen X scale), as DuckStation's widescreen hack does.
2. **Culling:** widen the game's culling and view checks to match, so objects don't pop in and out at the screen edges. DuckStation can't fix this; we can, at the source.
3. **2D elements:** the HUD, subtitles, menus and inventory are laid out for 320 wide. Squeeze them by 3/4 too, or they appear stretched on a 16:9 TV.
4. **4:3 elements:** pre-rendered and full-screen elements (movies, load screens, the title) stay 4:3 with black side bars.

**Independence:** widescreen is independent of the 720p work and can come before or after it.

**First measurements, either way:**
- **720p:** how many texture pages a busy scene needs per frame (texture streaming, step 1).
- **Widescreen:** a projection change tested in one area, to see what pops in at the edges.
